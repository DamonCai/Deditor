# 阅读编辑长文与连续编辑性能（2026-09-24）

用户反馈：Markdown 阅读编辑在文档较大、使用时间较长后明显卡顿。本轮仅使用仓库自建样例和新生成文档，未读取用户真实文档、历史记录或应用持久化状态；保留工作区既有 PlantUML 超时改动。

## 已确认的开销与改动

1. **撤销快照重复复制 AST**：每次输入导致后续块的源码偏移变化，旧实现递归复制所有后续块的语法树，历史快照持有这些副本。约 253KB、1000 段文档，150 个独立历史组额外保留约 245MB 堆。现在未改内容共享原树，仅按需投影偏移；连续偏移合并到最初原树，避免层层引用以前的输入。旧快照保持不可变，原有 500 组历史上限、分组和保存时机不变。
2. **标题定位标记整体重建**：每次文档变化都从头构造完整 DecorationSet，其构建重复扫描文档子节点。现在沿事务映射已有标记，仅替换位置/ID 不匹配项；重复标题、嵌套标题、原始块内标题占号、格式展开、删改和撤销继续使用原有规则。
3. **目录行随源码位置重建**：目录以标题位置作为 React key，在前部输入后，后续标题位置全变，导致大量目录行销毁重建。现在以不可变标题节点身份与出现序号保留行，导航仍使用最新位置。只改阅读编辑提供的可选 key，其他预览目录继续使用原有 ID。

不增加文档大小或内容限制，不缩短撤销历史，不延后内容提交或保存，不更改文件字节、目录导航目标、主题和显示规则。

## 测量方法

- 起点产品提交：`7025ef7`。对比时仅替换本轮产品文件为修改前副本，其他依赖及工作区状态相同。
- 实际阅读组件：`node scripts/perf-markdown-component-profile.mjs 1000`，真实 React/ProseMirror 组件 + JSDOM；每个进程测 5 次标题和 5 次正文输入，输入后撤销并断言源码精确一致。新增目录旧 DOM 保留计数。
- 历史模型：`node --expose-gc --import tsx scripts/perf-markdown-reading-soak.ts`，真实解析器、MarkdownDocument 和 MarkdownSession，1000 段、150 次独立编辑，GC 后比较保留堆增量；逐次撤销/重做与最终解析等价断言。可用 `DEDITOR_READING_BASELINE` 指向修改前文件根目录。
- 基准可复跑；默认历史基准已接入 `perf:all`。专项正确性已接入 `test:all`。
- 这些是模型/组件开销，不等同于原生 WKWebView 的按键到画面延迟。运行测试进程之外的系统负载无法完全控制。

## 对比结果

同机三轮串行、修改前/后交替执行。每轮输入取 5 次中位数，再取三轮中位数；内存取三次 GC 后增量中位数。

| 场景 | BEFORE | AFTER | DELTA |
| --- | ---: | ---: | ---: |
| 253KB 文档，150 组历史额外保留堆 | 245.33 MiB | 88.27 MiB | -157.06 MiB（-64.0%） |
| 742KB / 1000 节混合文档，正文输入 | 128.86 ms | 81.70 ms | -47.16 ms（-36.6%） |
| 相同文档，标题输入（含文内 TOC 刷新） | 362.00 ms | 303.98 ms | -58.02 ms（-16.0%） |
| 标题输入后重建的侧边目录行 | 1028.00 行 | 1.00 行 | -1027.00 行（-99.9%） |

正文三轮中位数：修改前 128.86 / 131.72 / 128.55ms，修改后 78.54 / 81.70 / 88.45ms。标题仍约 304ms，不能称完全消除卡顿。

释放历史后的堆增量：修改前约 4.78MiB，修改后约 6.62MiB（+1.85MiB）；不把保留堆改善当作整个进程 RSS 或长期泄漏结论。纯模型单次编辑三轮中位数约 1.87→1.81ms，差异小且有波动，不作为主要输入提速依据。

代价：每个历史快照仍有顶层索引及偏移投影对象，第一次访问后续块的子节点时才构造对应位置视图；不是零内存或全量虚拟化。目录/标记优化增加少量弱引用身份缓存，不引入外部服务。

## 验证轮次

- 轮 1 — 源码与定位边界。期望：偏移共享不污染旧快照，标题 ID 与全量重建一致。实测：20,000 次累积偏移及反向归零；重复/嵌套/原始块标题、正文输入、标题改名/删增、换节点类型、整篇替换与选区事务；LF/CRLF、表格/列表/脚注的 96 次混合编辑及源码位置逐项核对。结果：通过。
- 轮 2 — 连续编辑与规模边界。期望：历史可精确恢复，超过原有上限后仅淘汰最老的组。实测：150 次撤销/重做；300 段连续 600 个独立编辑后精确恢复保留的 500 组；10,000 段、约 2.55MB 文档 50 次编辑/撤销/重做；重置模型/会话后释放历史。结果：通过。
- 轮 3 — 真实浏览器交互。期望：长文编辑、保存快照、撤销重做、主题和独立标签一致。实测：内置 Chromium、1000 节混合文档，标题输入“检查”、保存快照、一次撤销/重做逐字核对；暗色切换、第二标签独立编辑/保存、返回首标签撤销并恢复原文。结果：通过。保存为自建页面内存快照，不冒充原生写盘。主题和长文重新挂载期间两次点击返回超时，随后观察确认动作完成且源码正确，不能算流畅度通过。
- 轮 4 — 全量回归与构建。期望：本次内部优化不改变其他编辑操作。实测：完整 `test:all`（含 62 核心、107 阅读集成、表格/剪贴板、保存/关闭/组合输入、导航、跨块操作及错误恢复）通过，TypeScript 与生产构建通过；独立标识的 macOS debug `.app` 构建通过，未启动或替换日常应用。结果：通过。
- 轮 5 — 同机性能对比及资源释放。期望：确认收益、保留原有性能回归边界。实测：修改前/后三轮串行对比见上表；完整 `perf:all` 通过，含 Rust 5,000 文件磁盘矩阵、既有 Markdown 输入/预览/目录/表格/多标签/组件性能和新增历史保留堆断言。最后套件历史样本 88.31MiB、重置后 6.66MiB。结果：通过。

## 范围与剩余

- 已定位并减少连续编辑的重复历史数据及每次输入的标题/目录重建。没有复现并证明持续数小时的原生内存泄漏，不将本轮结果当作全部长期性能验收。
- 千节混合文档的首次打开、主题切换及重新挂载仍有明显开销；标题修改还会更新文内 TOC。未实施整页虚拟化，也不称任意大文档无卡顿。
- 独立测试包：`src-tauri/target/debug/bundle/macos/DEditor Reading Review.app`，独立 bundle ID `com.deditor.readingperf20260924`，无文件关联；包含当前工作区原有改动。仅构建，未声称原生实际验收。
- 未新增原生 WKWebView、系统拼音候选、Windows 或图床结论。测试页面和临时服务已关闭；未替换日常应用，未提交、未推送。
- 原始数据与日志：`tests/artifacts/reading-performance-2026-09-24/`（忽略目录，跨机另行迁移）。
