# XMind 性能审计

用户询问仍可优化的性能。本次只运行自建数据的生产函数测量，没有启动桌面应用，也没有修改运行时代码。证据为 `tests/artifacts/xmind-performance-audit-20260912/results.json`，包括测量源码哈希。

## 实测

Node v23.11.1 / macOS；每项预热一次、测量三次，以下为中位数毫秒。附件为随机不可压缩字节，避免可压缩全零附件掩盖实际归档大小。这些是计算阶段数据，不包含真实浏览器绘制、原生 IPC、磁盘写入和垃圾回收归因。

| --- | ---: | ---: | ---: | ---: |
| 1,001 节点，无附件 | 0.90 | 0.71 | 0.09 | 13.89 |
| 5,001 节点，无附件 | 2.62 | 2.62 | 0.36 | 60.77 |
| 1,001 节点，8MiB 附件 | 0.54 | 0.88 | 145.02 | 10.82 |

## 可优化顺序

1. **避免每次提交编辑都转换整份归档。** `XmindView.publish` 在主题/格式/折叠/撤销等提交时同步 `writeDocument`，再转整份 Base64 放入 store。8MiB 附件案例产出约 1,119 万字符的 data URL，Base64 是本次最大开销。已有 ZIP 修改保留附件压缩流，不能再描述为每次重新压缩附件。可研究会话文档与保存快照分离、相同版本序列化缓存和更高效的字节编码；须同时保住 dirty、未离焦保存、自动保存、外部修改和恢复语义。画布标题草稿每个字不经过 publish，不能把该开销误说成每次按键都发生。
2. **减少整图布局和文本测量。** `scene` 依赖整个 sheet，修改一个不影响尺寸的颜色或备注也会使布局重新计算。可按内容/几何变更区分失效范围，缓存文本尺寸及未受影响的子树；需保护主题继承、嵌套边界、折叠和鱼骨避让。5,001 节点布局约 61ms，值得优先处理。
3. **减少草稿输入和拖动时的 React 工作。** `sceneContent` 将全部可见结构节点映射成元素，依赖 draft 和 dragOffset。输入一个主题或拖动一组主题仍会重建/核对整组元素；这不等于所有 DOM 都被替换。可拆分稳定节点与编辑/拖动层，复用未变节点，对 pointermove 按帧合并，再评估视口裁剪。须保留画布外选中项、搜索定位、辅助访问和跨屏联系。
4. **降低编辑及历史内存成本。** `editDocument` 每次深拷贝当前 sheet，遍历新旧主题集合，再分别 JSON.stringify 判空修改；history 保留最多 50 个前态。可对无效修改提前返回、按操作收窄引用清理范围，使用结构共享减少历史复制。附件并未被每个历史状态深拷贝，不能将 50 步历史误算成 50 份附件。本次未直接测量堆内存，内存收益须进一步取证。

现有基准不覆盖 `publish` 的 Base64 和真实 React 更新，因此旧的布局/保存基准通过不能证明完整编辑链路流畅。后续应在固定源码快照中补这些阶段的基准及真实浏览器连续操作，并和保存/撤销一致性一起验收。以上均为待实施优化，不计作已优化完成。
