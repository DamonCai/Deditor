## 优先处理：状态持久化与历史

`src/lib/persistence.ts` 已有 500ms 防抖和串行写入，干净的具名文件及二进制不持久化全文。但脏文档仍同时携带当前正文与保存前正文。应用状态订阅也会因光标和其他界面状态变化触发持久化，因此未变正文仍可能重复传输和写入。

`src-tauri/src/lib.rs::write_app_state` 先写临时文件再重命名，之后完整解析 JSON，遍历所有脏 Markdown 文档记录草稿。`markdown_history::record` 缓存了历史元数据，但每次去重仍读取上一份历史全文。

自建临时数据，release 优化，调用实际历史实现，7 次暖缓存中位数：

| 场景 | JSON 大小 | JSON 解析 | 重复历史核对 | 状态写入及重命名 | 完整链路 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 个 1MiB 脏文档 | 2.12MiB | 1.486ms | 0.599ms | 0.600ms | 2.505ms |
| 20 个 1MiB 脏文档 | 42.43MiB | 29.861ms | 10.400ms | 9.093ms | 50.654ms |

各列独立取中位数，不应相加当作完整链路中位数。20 文档重复测量约 50–58ms；还会读取约 20MiB 上次历史正文。结果不含前端序列化、IPC、原生调度等待，不是用户整体卡顿时间。

另一个已确认的浪费：保存 Markdown 时无条件读取原文件，再交给历史层；历史层拒绝超过 2MiB 的内容，因此大文件读完也不会记入历史。20MiB 自建文件暖读取约 3.410ms，并创建同等大小的临时字符串。

建议顺序：

1. 按正文是否变化跳过重复草稿检查，减少历史全文读取；任何缓存需有容量上限及删除、损坏失效处理。
2. 避免无关界面状态变化反复携带和解析未变全文。涉及持久化协议，应单独实现并验证恢复、关闭及失败顺序。
3. 限制保存前的历史原文读取，避免读取最终不接受的大文件。

必须保留旧历史、主文档写入、新历史的顺序；主保存失败仍返回错误，历史失败仍仅警告；状态串行覆盖和关闭前 flush 不能丢失。现有历史有 2MiB 单版本、100MiB 总量、单路径 30 份及总计 1000 份上限。30 秒草稿合并发生在写入新版本后，不等于减少写盘频率。全局历史锁还覆盖磁盘读写，后续工作线程调整应一并考虑顺序与竞争。

## 搜索、替换与传输

- 已发出的工作区搜索没有取消机制。前端请求编号只丢弃旧结果，已开始的后端遍历和读盘会继续。可增加协作式取消，保留正常请求的排序、截断和扫描计数语义。
- Unicode 忽略大小写搜索在知道是否命中前，就创建完整字符位置映射。可延后到命中再计算，必须保留大小写扩展、希腊文上下文和 UTF-16 列号。
- 批量替换逐文件规范化同一个查询，无匹配文件也分配输出字符串。可以共享查询并延后输出分配，保持错误顺序及部分成功语义。
- 二进制读取同时持有原字节与 Base64 字符串，已有 50MiB 上限。传输协议调整需要真实大文件内存和 IPC 测量，不能仅凭代码推断收益。

这些重复工作已由代码确认，优化收益尚未测量。同步 Rust 命令没有显式将重工作分派到独立队列，但本次未测原生线程和交互延迟，不能宣称它们全部阻塞 UI 主线程。
