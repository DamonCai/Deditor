更新：本表前三项的代码高亮缓存、过期图表跳过与滚动索引已实施，见 [实施与剩余排序](markdown-preview-performance-implementation-2026-09-12.md)。未变 SVG 复用仍待评估；下方原始测量保留为诊断历史。

## 建议顺序

| 顺序 | 优化项 | 当前证据 | 建议范围与边界 |
| --- | --- | --- | --- |
| 1 | 未改代码块高亮缓存 | `Preview.tsx:103` 每次源码更新调用全文渲染；`markdown.ts:258` 遍历全部普通围栏高亮。只修改普通段落，100 个代码块仍高亮 100 次，函数耗时约 163ms | 先按代码内容、语言、主题缓存，限制缓存容量。无需先重写 Markdown 解析器 |
| 2 | 过期图表跳过、未变图表复用 | `mermaidHydrate.ts:71` 等待串行队列后，真正开始渲染前没有再次检查取消状态；新预览 DOM 失去旧 hydrated 标记 | 先丢弃排队期间过期的任务；后续再复用图表。保护 SVG ID、交互绑定、主题和导出隔离 |
| 3 | 滚动行号/位置索引 | `Preview.tsx:154`、`:375` 在双向滚动时查询全部 `[data-line]` 并读取每个 offsetTop，然后线性搜索。已有 rAF 节流，但每帧仍做全文工作 | 缓存行号与几何位置，二分查找；图片、图表、宽度与字号变化时失效，保留贴底语义 |
| 4 | 长文输入的源码坐标与历史更新 | `document.ts:149`、`:283`、`:331` 局部编辑后仍复制 AST 位置信息；`markdownSession.ts:73` 再次从两端逐字符计算全文差异；`document.ts:480` 光标定位仍遍历顶层块 | 将已知 patch 传给历史；先去除空选区坐标重复计算，再评估块内相对偏移索引。必须保护原文、选区与跨模式撤销 |
| 5 | 模式/主题切换与大 DOM 重新显示 | 当前阅读实例已跨模式保留，但源码→阅读样例仍约 485ms，updateState 仅 0.1ms；样例阅读 DOM 含 42,100 个后代元素。`MarkdownVisualEditor.tsx:376` 的 effect 依赖主题/语言/路径，变更还会重建编辑器 | 分开测量 DOM 布局、组件更新、静态块显示；优先推迟屏幕外昂贵块。主题更新与编辑器实例生命周期解耦需独立验证，不先做全编辑器虚拟化 |
| 6 | 后台预览与跨模式预览缓存 | `Preview.tsx:103` 渲染 effect 不受 active/retainDom 限制；`App.tsx:538` 离开预览会卸载 PreviewHost，回来重新生成 | 按文档版本保留结果，后台只标记过期，显示前补齐。保留已有 DOM 数量上限，避免无限保留大页面 |
| 7 | 标题/大纲/搜索索引 | `headingIds.ts:13` 以整个 doc 为缓存键，正文变动后重新遍历；大纲打开时另做全文扫描；搜索已缓存匹配，但打开时每次输入仍遍历文本块并复制结果 | 共用标题索引、映射未变位置；固定查询只重搜变化块。大纲/搜索关闭已经停算，不重复优化已解决部分 |

额外低成本候选：纯文字文档的 `renderMarkdown` 仍先等待 `getHighlighter()`（`markdown.ts:211`）；可在确有普通代码围栏时才启动。当前语言语法和 KaTeX 已按需加载，PlantUML 已有缓存，不应当成缺失。

## 本轮测量及解释

1. **实际渲染函数，Node 环境**：自建 57,116 字符、100 个 TypeScript 围栏、每块 20 行。预热后仅修改文末普通段落，三次高亮调用均为 100；耗时 163.48 / 163.49 / 162.39ms。这不含 HTML 清理、DOM 挂载和浏览器布局，也不是整页输入时延。
2. **当前开发页，实际按键**：6,303 行、152,241 字符、500 个附加表格，定位到文末正文后实际输入 q/w/e；从按键到第二动画帧为 92.0 / 91.8 / 110.3ms，中位数 92.0ms。对应输入事件阶段约 19.2–22.7ms，updateState 8.5–9.5ms，document.apply 2.8–3.7ms。显示前的其余耗时不能仅凭这些计时归因为解析或布局，需进一步浏览器性能剖析。
3. **当前开发页模式往返**：撤销三次后全文与初始文档逐字一致；切源码 159.1ms、返回阅读 484.7ms，返回时 updateState 0.1ms，未观察到 reset/index 计时。仅单次模式样本，不是统计性能承诺；说明不能继续把所有模式卡顿称为全文重解析。
4. **已有局部优化仍有效**：现有行内源码控制器 JSDOM 基准，1000 段普通文档未改收起约 0.62ms，局部修改收起约 0.84ms。基准主动关闭局部路径的对照约 78.19ms；这是验证已有机制，不是本轮优化收益。
5. **复杂局部编辑还有规模开销**：扩展同一控制器基准至 500 节、87,169 字符、500 条脚注定义，普通多行/嵌套/表格的收起中位数约 30.17 / 40.72 / 40.71ms；全文 parse 计数只有初始化 1 次。说明局部路径仍受定义上下文、索引和 DOM 更新规模影响，不能误报为每次完整 parse。
6. **不列为首要瓶颈**：当前 78 万字符统计基准，100 次增量更新合计中位数 6.87ms；2000 任务控件局部更新中位数 0.024ms。仅模块微基准，不包含浏览器布局。

第一次直接运行旧 `perf-markdown-inline.ts` 因 JSDOM 未补 `matchMedia` 而失败；在被忽略的临时副本仅补环境接口后运行通过，再扩展 500 节规模。没有修改产品或原性能脚本。证据及临时副本在 `tests/artifacts/markdown-performance-audit-2026-09-12/`。

首次用自动化单键事件试探时原文未改变，该条 20.9ms 被排除，不计为输入性能证据。实际 q/w/e 使用了有 beforeinput/input 且原文可核验的输入路径。

以上不是优化后的承诺或跨版本对跑；开发构建、仪器开销与机器负载会影响数字，不能拿本轮 92ms 直接对比历史生产页 70ms 来判断回退。真实 IME、macOS/Windows 安装包和长期内存压力本轮未重新验收。
